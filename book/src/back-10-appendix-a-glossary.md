## A.1　对象与存储

**对象（object）** — Git 对象库里的一个不可变单元，共四种：blob / tree / commit / tag。**易混点**：对象一旦写入就永不修改，所谓"改历史"是造新对象再移动引用（第 1、9 章）。

**对象库（object database，`.git/objects/`）** — 存放全部对象的地方，内容寻址、只追加。**易混点**：对象库不可变，但它"看起来会变小"——那是 `gc` 删掉了不可达对象，不是修改了对象（第 2、10 章）。

**内容寻址（content-addressable storage）** — 用"内容的哈希"当键，而不是文件名或版本号。**易混点**：哈希的输入不是裸内容，而是 `类型 空格 长度 NUL 内容`（第 2 章）。

**blob** — 文件内容的字节串，**不含文件名、不含权限、不含路径**。**易混点**：因为不含文件名，两份内容相同的文件只存一份 blob，重命名也不会产生新 blob（第 2 章）。

**tree** — 一层目录的列表，每行是 `模式 类型 哈希<TAB>名字`。**易混点**：tree 只描述"这一层"，子目录是另一棵 tree 的哈希引用；tree 里没有"上一版"的信息（第 1、2 章）。

**commit** — 一次快照的元数据：`tree` + 0 个或多个 `parent` + `author` + `committer` + 信息。**易混点**：`author` 与 `committer` 可以不同——rebase 后内容不变但 committer 变成执行者（第 2、9 章）。

**tag 对象** — 第四种对象，指向另一个对象并带 `tagger`、日期与说明，可签名。**易混点**：只有 `git tag -a`/`-s` 才产生它；轻量标签不产生对象（第 3、11 章）。

**轻量标签（lightweight tag）** — 一个直接指向 commit 的引用，`git cat-file -t` 显示 `commit`。**易混点**：它**没有地方放发布说明**，也无法签名，所以发布不该用它（第 3、11 章）。

**附注标签（annotated tag）** — 由 `git tag -a` 创建，是独立对象，`git cat-file -t` 显示 `tag`。**易混点**：`git tag -l` 看不到它的说明，要用 `git for-each-ref --format='%(subject)'` 或 `git show`（第 3、11 章）。

**空树对象（empty tree，`4b825dc642cb6eb9a060e54bf8d69288fbee4904`）** — 一棵没有条目的 tree，因为 `tree 0\0` 的 SHA-1 恒定，所以是所有仓库通用的常量。**易混点**：它不是魔法数字，任何仓库都能用 `git hash-object -t tree /dev/null` 复现（第 2 章实测）。

**松散对象（loose object）** — 一对象一文件，存在 `.git/objects/xx/yyyy…`，zlib 压缩。**易混点**：文件名是"哈希前 2 位当目录 + 后 38 位当文件名"，分片是为了避免单目录堆几十万个文件（第 2 章）。

**packfile** — 把大量对象打包进一个 `.pack`（配 `.idx` 索引），并做 delta 压缩。**易混点**：`cat-file`/`diff` 对"松散还是打包"完全透明，你自己读 `.git/objects` 却必须两种都处理（第 2、3 章）。

**delta / delta 链（delta chain）** — packfile 里只存"与基准对象的差异"，相似对象串成链。**易混点**：深链省空间但读取要依次还原；`--depth=1` 禁止深链会让体积涨 **5.6×**（第 10 章实测）。

**chain length（链长）** — 某个对象所在的 delta 链长度，用 `git verify-pack -v <idx>` 看直方图。**易混点**：它反映的是**存储**结构，与你 `git log` 看到的提交图毫无关系（第 2、10 章）。

**commit-graph** — 预计算的提交元数据文件（父提交、提交时间、根树位置），让遍历不必逐个解压 commit。**易混点**：它只加速**纯遍历**（`rev-list`、`log --graph`，实测 3.4×），对"读对象取内容"和短命令几乎无影响（第 10 章）。

**bitmap（`.bitmap` 文件）** — 把"某提交可达的对象集合"编码成位图，把服务端算"要发哪些对象"变成位运算。**易混点**：它优化的是**服务端**的 `pack-objects` 可达性计算，本地小仓库测不出差异（第 10 章）。

**multi-pack-index** — 多个 packfile 之上的一层索引，避免逐个读 `.idx`。**易混点**：它不合并 pack，只是让查找更快（第 10 章）。

**SHA-1 / SHA-256** — 对象 ID 的哈希算法；`git init --object-format=sha256` 可建 SHA-256 仓库。**易混点**：Git 哈希的**结构**（类型头 + 长度 + NUL + 内容）两种算法完全一致，只是摘要长度不同（第 2 章）。

**哈希碰撞（SHAttered）** — 2017 年公开演示的 SHA-1 碰撞，需要巨量算力。**易混点**：Git 不是直接哈希裸内容，攻击面比"裸 SHA-1"小；但迁移到 sha256 仍是有价值的长期选项（第 2 章）。

**对象可达性（reachability）** — 从某个引用出发、顺着 parent/tree 能否走到该对象。**易混点**：可达性是**相对引用**说的——同一个对象在打了 tag 之后就从"吊着的"变成"可达的"（第 3、9 章）。

**dangling（吊着的对象）** — 对象库里存在、但没有任何引用（含 reflog）能到达的对象。**易混点**：dangling ≠ 会被立刻删除，只有"过期 + 不可达"才会被 `gc` 清掉（第 3 章）。

**`git fsck`（file system check）** — 校验对象完整性与可达性，`--lost-found` 会把吊对象写进 `.git/lost-found/`。**易混点**：`--unreachable` 只列不写；它是**恢复的第三层**，不是第一层（第 3、9 章）。

## A.2　引用与历史

**引用（ref）** — 一个装着 40 位哈希的文本文件（41 字节含换行），存在 `.git/refs/`。**易混点**：引用可以被打包进 `.git/packed-refs`，**永远不要自己读 `.git/refs/`**，要问 `git rev-parse`/`git for-each-ref`（第 3 章）。

**分支（branch）** — `refs/heads/` 命名空间下的一个引用。**易混点**："创建分支"字面上就是写一个 41 字节的文件，所以极廉价（第 1、3 章）。

**松散引用 vs 打包引用** — 松散在 `.git/refs/…`，打包在 `.git/packed-refs`；两者同时存在时**松散优先**。**易混点**：一次 `git gc` 或 `git pack-refs` 就能把引用搬进 packed-refs，代码若假设"引用在文件里"就会随机失效（第 3 章）。

**HEAD** — 特殊引用，通常是一个**符号引用**（装着 `ref: refs/heads/x`），表示"我现在在哪个分支上"。**易混点**：`git symbolic-ref HEAD` 问"名字"、`git rev-parse HEAD` 问"值"，detached 时前者失败后者成功（第 3 章）。

**符号引用（symbolic ref）** — 内容是"另一个引用的名字"而不是哈希的引用，`.git/HEAD` 就是。**易混点**：unborn HEAD（刚 `git init`）时 `.git/refs/heads/main` **并不存在**，但 `symbolic-ref --short HEAD` 仍然成功（第 3 章实测）。

**detached HEAD** — HEAD 直接指向一个提交而不是分支。**易混点**：此时 `git symbolic-ref HEAD` 报 `fatal: ref HEAD is not a symbolic ref`，但 `rev-parse HEAD` 照常工作——所以取值与取名字必须分开写（第 3 章）。

**unborn HEAD（无提交仓库）** — `git init` 之后、第一次提交之前的状态。**易混点**：`symbolic-ref` 成功、`rev-parse HEAD` 失败（退出码 128）；diff 的基准要回落到空树（第 3 章）。

**reflog** — 记录"引用是怎么移动的"的本地日志（`.git/logs/HEAD`、`.git/logs/refs/…`）。**易混点**：它是"历史的历史"，不是历史本身；**clone 不会带上别人的 reflog**，且救援动作本身也会被记进去（第 3、9 章）。

**reflog 过期** — `gc.reflogExpire`（默认 90 天）与 `gc.reflogExpireUnreachable`（默认 30 天）。**易混点**：事故后"别急着 gc"是有依据的——reflog 还在就能救（第 3 章）。

**`ORIG_HEAD`** — `reset`/`merge`/`rebase` **之前**的位置，恢复的第一层"一枪救回"。**易混点**：它只有**一个**槽位，会被下一次操作直接覆盖，所以它是三层里最先失效的那层（第 3、9 章）。

**`FETCH_HEAD`** — 上一次 `fetch` 抓到了什么；`git merge FETCH_HEAD`/`git pull` 会用它。**易混点**：`fetch` 改了 `FETCH_HEAD` 与 `refs/remotes/*`，**但绝不动你的本地分支和工作区**（第 3、8 章）。

**`MERGE_HEAD` / `CHERRY_PICK_HEAD`** — 正在合并 / 正在 cherry-pick 的"对方"提交。**易混点**：这些文件**存在与否本身就是仓库状态**——`.git/MERGE_HEAD` 存在即"合并未完成"（第 3 章）。

**引用命名空间（`refs/heads`、`refs/tags`、`refs/remotes`）** — 引用按用途分区。**易混点**：`refs/remotes/origin/main` 是**你本地的一份只读镜像**，不是远端本身；它不是分支，不能直接 commit 上去（第 3、8 章）。

**revspec（修订表达式）** — 引用系统的表达式语言，如 `HEAD~2`、`main^{commit}`、`HEAD@{1}`。**易混点**：规则极多，别自己实现——交给 `git rev-parse`，再包装它的报错（第 3、12 章）。

**`~` 与 `^`** — `~<n>` 沿**第一父**往回 n 代；`^<n>` 取第 n 个父。**易混点**：`^` 默认等于 `^1`；合并提交上 `HEAD~1` 与 `HEAD^1` 恰好相同，但 `HEAD~2` 与 `HEAD^2` **完全不同**（第 3、5 章）。

**`@{n}` 与 `@{time}`** — `HEAD@{1}` 是 reflog 里的上一步，`main@{2.hours.ago}` 按时间取。**易混点**：`HEAD@{1}` 是"你的操作史"，`HEAD~1` 是"历史的形状"，两者在 rebase 后会分道扬镳（第 3、9 章）。

**`^{commit}`（剥壳，peel）** — 一路剥到 commit：tag 对象 → 它指向的提交。**易混点**：附注标签的哈希指向 tag 对象而非提交，所以 `rev-parse --verify <rev>^{commit}` 才是校验"用户给的是不是提交"的正确写法（第 3、5、8 章）。

**DAG（有向无环图）** — commit 的 `parent` 边构成的图。**易混点**：不可能成环，因为 commit 的哈希包含父哈希——你无法构造一个自己是自己祖先的对象（第 1、5 章）。

**parent（父提交）** — commit 里指向上一个提交的字段，0 个 = 根提交，2 个及以上 = 合并提交。**易混点**：`parent` 的顺序有意义，第一条是"接收方"（第 2、5 章）。

**first-parent（第一父）** — 合并提交的两条父边里，"我刚才站在的那条线"。**易混点**：`git log --first-parent` 会把特性分支的中间提交折叠掉；对合并做 diff 时取 `HEAD^1` 等价于 GitHub 的 PR diff（第 5 章）。

**octopus merge（章鱼合并）** — 一次合并 3 条以上分支，产生 3 条以上父边的合并提交。**易混点**：Git 支持它，但**不能用来解决冲突**（有冲突时它会直接拒绝），这是它少见的真正原因（第 5 章）。

**merge-base（共同祖先）** — 两个提交在 DAG 上的最近公共祖先，`git merge-base A B` 求它。**易混点**：criss-cross 场景下可能有**多个** merge-base，默认只返回一个，要全部得加 `--all`（第 5 章）。

**fast-forward（快进）** — 目标分支是当前分支的祖先时，只移动指针、**不产生新提交**。**易混点**：`--ff-only` 会在不能快进时直接报错，是 CI 里防止意外合并提交的常用闸（第 5 章）。

**`--no-ff`** — 强制产生一个合并提交，即使快进可行。**易混点**：它的价值是让"这个特性是一个整体"在图里永久可见；代价是历史不再是直线（第 5 章）。

**合并提交（merge commit）** — 有两条及以上父边的提交。**易混点**：`git show <merge>` 默认**什么都不显示**，因为"改动"取决于和哪个父比；要么 `git show -m`，要么显式写 `HEAD^1..HEAD`（第 5 章）。

**双点 `A..B`（diff 语义）** — 两个尖端**直接**比。**易混点**：它会把 A 自己的新增反向算成"B 删掉了它"，所以 PR 审查用它会看到一处根本不存在的删除（第 5 章实测 3 个文件 vs 2 个文件）。

**三点 `A...B`（diff 语义）** — 从 `merge-base(A,B)` 比到 B，等价 `git diff $(git merge-base A B) B`。**易混点**：同一个符号在 `git log` 里语义不同——`log A...B` 是"两边独有的提交"（对称差）（第 5 章）。

**`reset --soft/--mixed/--hard`** — 三模式分别动三棵树里的：只 HEAD / HEAD+索引 / 三棵全动。**易混点**：`--hard` 是唯一会**丢工作区改动**的——那些改动从没进过对象库，真的救不回来（第 9 章）。

**revert** — 造一个**反向提交**来抵消某次改动，历史只增长。**易混点**：它和 `reset` 完全相反——`revert` 可以安全地用在已推送的公共分支上（第 9 章）。

**cherry-pick** — 把某个提交的 diff 重新应用到当前分支，产生**新哈希**的新提交。**易混点**：它复制的是"改动"不是"提交"，所以父提交不同、哈希必然不同（第 9 章）。

**rebase** — 把一串提交逐个重放到新基底上，产生一串全新提交。**易混点**：reword 一个提交会让**下游所有哈希**都变，所以已推送的分支 rebase 后必须 force push，且同事的历史会分叉（第 9 章）。

**amend** — 用当前索引内容重造"上一次提交"，产生新对象。**易混点**：`--amend` **不会**修改原对象，原提交仍在磁盘上、仍可按哈希读出（第 9 章实测）。

**squash / reword / drop（交互式 rebase 指令）** — 压扁 / 改信息 / 丢弃某次提交。**易混点**：`drop` 撤的是"改动"不是"文件"——后续提交若依赖它，必然冲突（第 9 章实测）。

**`git filter-branch`** — 老的历史清理工具，重写全部历史且很慢。**易混点**：Git 已不推荐它（启动时会自己打印警告），并会留下 `refs/original/*` 备份引用；官方推荐 `git filter-repo`（第 9 章）。

## A.3　索引与工作区

**索引（index / staging area，`.git/index`）** — 二进制文件，魔数 `DIRC`，是**下一次提交的候选快照**。**易混点**：它不只是"暂存区"，还是**合并工作台**（冲突时同一路径有 stage 1/2/3）与**stat 缓存**（第 4 章）。

**三棵树（HEAD / 索引 / 工作区）** — 日常操作的全部舞台。**易混点**：`git status` 的**两列**正好对应两条边——第一列是 HEAD↔索引（staged），第二列是索引↔工作区（unstaged）（第 4 章）。

**staged（已暂存）** — **索引里的内容与 HEAD 不同**。**易混点**：staged 不是你"运行过 add"，而是"索引与 HEAD 不一致"这个**事实**；`git reset <f>` 后它就不再 staged 了（第 4 章）。

**unstaged（未暂存）** — **工作区与索引不同**。**易混点**：与 untracked 不同——unstaged 的文件是**已被跟踪**的（第 4 章）。

**untracked（未跟踪）** — 工作区里有、索引里没有的文件（`??`）。**易混点**：`git status --porcelain` 里它的第一个字符是 `?`，不遵循"两列"语义（第 4 章）。

**`MM` 状态** — 先 `add`、又改了工作区，同一个文件两份内容并存。**易混点**：`git commit` 提交的是**索引里那一份**，工作区那部分完全不进这次提交（第 4 章）。

**`git add -p`** — 交互式按块暂存，本质是"拼一个只含部分改动的 blob 放进索引"。**易混点**：它是"部分提交"的基础，而不是某种特殊的提交方式（第 4 章）。

**stage 1/2/3（冲突条目）** — 冲突时同一路径在索引里有三条记录：1 = 共同祖先（base）、2 = ours、3 = theirs。**易混点**：`git ls-files -s` 输出中间那个数字就是 stage 号，正常是 0（第 4 章）。

**解决冲突（resolving conflict）** — 在 Git 内部就是**一次 `add`**，把三条归一成 stage 0。**易混点**：工作区里的 `<<<<<<<`/`=======`/`>>>>>>>` 只是给人看的文本提示，真正的三方数据在索引里（第 4 章）。

**stat 缓存（ctime / mtime / dev / ino / uid / gid / size）** — 索引条目里的文件元信息，让 `git status` 不必读内容就能判断谁变了。**易混点**：这是索引的"第一个身份"，与暂存无关；第 10 章讲的 `core.fsmonitor`/`untrackedCache` 都是它的延伸（第 4、10 章）。

**`git ls-files -s`** — 列出索引条目（模式 / blob 哈希 / stage 号 / 路径）。**易混点**：中间那个数字是 **stage**，不是大小，也不是权限（第 4 章）。

**`git update-index --assume-unchanged`** — 告诉 Git"别检查这个文件的变化"，是**性能手段**。**易混点**：它**不是** `.gitignore` 的替代品，克隆到别处就失效，还可能导致改动被静默忽略（第 4、7 章）。

**`git update-index --skip-worktree`** — 让 Git 忽略工作区版本（常用于本地配置覆盖）。**易混点**：`git pull` 撞上它时会报冲突——它同样不是 ignore（第 4、7 章）。

**worktree（链接工作区，`git worktree`）** — 同一个仓库挂载多个工作区，各自可以检出不同分支。**易混点**：它们**共享同一个 `.git` 对象库与引用**，所以不是"多克隆"（第 1 章）。

**`.gitkeep`** — 一个纯约定：Git 不跟踪空目录，放个空文件让目录能被提交。**易混点**：它**没有任何特殊功能**，任何文件名都一样（第 7 章）。

## A.4　差异与传输

**diff（差异）** — 两个快照现算出来的最小编辑脚本，**Git 从不存储它**。**易混点**：这也是"重命名显示为删除+新增""合并 `git show` 是空的""输出取决于配置"三件事的共同原因（第 6 章）。

**Myers 算法** — Git 默认的 diff 算法：在编辑图上找最短路径，复杂度 O(ND)。**易混点**：它找的是"最短"，不是"最符合人眼"；重复行一多，两者就冲突（第 6 章）。

**`--diff-algorithm`** — 在 `myers`/`minimal`/`patience`/`histogram` 之间选算法。**易混点**：普通改动上四者输出一致，只有在"重复块被搬动"时才分道扬镳（实测 patience 16 行 vs 其余 6 行）（第 6 章）。

**unified diff** — 默认的 diff 文本格式，含 `diff --git`、`index`、`---`、`+++`、`@@` 与正文行。**易混点**：`diff --git a/x b/x` 是**协议行**，不是真正的 diff 行，不能当路径来源（第 6 章）。

**hunk（差异块）** — 一段连续改动，由 `@@` 头引导。**易混点**：hunk 头 `@@ -1,4 +1,5 @@` 里四个数字分别是"旧起点,旧行数 新起点,新行数"，且起点是 **1-based**（第 6 章）。

**index line（`index 84275f9..07685c9 100644`）** — 记录旧 blob 哈希 `..` 新 blob 哈希 + 文件模式。**易混点**：这里的 `index` 是"新旧 blob 的索引对"，与暂存区（index）**同名但不同事**（第 6 章）。

**`\ No newline at end of file`** — 标注**上一行**没有以换行结尾。**易混点**：它以 `\` 开头，天然不会被"按 `+`/`-` 计行"的逻辑误判；真正危险的是 `+++ `/`--- ` 这两条协议行（第 6 章）。

**前缀 `a/` `b/`** — diff 头部的人为前缀，让路径在"仓库根"前提下像相对路径。**易混点**：它**可被用户配置改写**（`diff.mnemonicPrefix` → `i/`/`w/`，`diff.noprefix` → 无前缀），所以工具必须显式固定 `--src-prefix`/`--dst-prefix`（第 6、12 章）。

**rename detection（重命名检测，`-M` / `--find-renames`）** — 靠**内容相似度**推断改名，默认阈值 50%。**易混点**：因为 blob 不含文件名，"改名"这件事根本不在内容里，只能推断；`-M` 的成本是"删除的文件 × 新增的文件"两两比较（第 2、6 章）。

**`-C`（copy 检测）** — 比 `-M` 更贵：还要在删除的文件与新增文件之间找相似块。**易混点**：日常几乎不需要它，大重构上它会显著变慢（第 6 章）。

**textconv** — `.gitattributes` + `diff.<driver>.textconv` 让 Git 先把内容"翻译"成文本再 diff。**易混点**：用户配的命令**执行失败时 `git diff` 直接退出 128**——所以工具必须传 `--no-textconv`（第 6、12 章实测）。

**`--no-ext-diff`** — 挡掉用户配置的**外部 diff 程序**（`diff.external`）。**易混点**：外部程序产出任意格式，任何解析器都会错，所以它不是洁癖式加固（第 6、12 章）。

**二进制判定（binary detection）** — Git 的规则是"**前 8000 字节里有没有 NUL**"（`buffer_is_binary`）。**易混点**：按字节截断的窗口会把"切在多字节字符中间"的合法 UTF-8 误判成二进制——这是真实踩过的 P0（第 6 章）。

**`core.quotepath`** — 控制非 ASCII 路径是否被转义成 `\344\275\240` 这类八进制。**易混点**：默认是转义的，所以工具几乎总要 `-c core.quotepath=false`，否则中文路径解析全错（第 8、12 章）。

**`core.filemode`** — 是否信任文件的可执行位。**易混点**：Windows 上设置不当时模式位会"变"，表现为"改了一个文件，diff 里却整文件变化"（第 2 章）。

**`.gitattributes`** — 按路径给文件配属性（`text`、`diff`、`export-ignore`、`filter` 等）。**易混点**：它的 `export-ignore` **只影响 `git archive`**，与忽略规则毫无关系（第 7 章）。

**`.gitignore` 的五个来源** — 命令行（`git add -f` 等）> `.gitignore`（**就近/深者优先**）> `.git/info/exclude` > `core.excludesFile`；`.gitattributes` 的 `export-ignore` 不算忽略来源。**易混点**：同一个文件内是"**最后一条命中的规则**"生效，所以**顺序是语义的一部分**（第 7 章）。

**`abc/**` vs `abc/`** — `abc/**` 匹配 `abc` **内部**（零层的 `**` 不被允许，**不含 `abc` 自身**）；`abc/` 匹配目录 `abc` 并且其下内容一并忽略。**易混点**：前导 `**/` 则**必须**允许零层，否则根目录下的 `foo` 匹配不到——两个方向相反，很容易写反（第 7 章实测）。

**`git check-ignore -v`** — 告诉你"**被哪个文件的第几行、哪条模式**命中"，格式 `来源文件:行号:模式<TAB>路径`。**易混点**：被 `!` 负向规则命中时它也会列出来，但退出码是 1（= 没被忽略）；一次传多个路径时，**只要有一个不被忽略就整体退出 1 且不打印任何内容**（第 7 章）。

**`git check-ignore --no-index`** — 连**已跟踪**文件也按规则判定。**易混点**：`.gitignore` 只管**未跟踪**文件，已跟踪文件照常显示修改、照常被提交；要让它脱离版本控制得 `git rm --cached`（第 7 章）。

**父目录被排除后 `!` 救不回** — Git 的规则：无法重新纳入一个"父目录已被排除"的文件。**易混点**：因为遍历到 `a/b` 发现被忽略就**不再往里走**，`a/b/c` 根本没被"看见"，所以 `!a/b/c` 无效（第 7 章实测）。

**partial clone（部分克隆，`--filter=blob:none`）** — 克隆时不要 blob，需要时再按需拉取（promisor 机制）。**易混点**：两个**静默陷阱**——本地路径克隆会忽略过滤（要用 `file://`），服务端没开 `uploadpack.allowFilter` 时只是警告然后退化成完整克隆（第 10 章实测）。

**sparse checkout（稀疏检出）** — 只把需要的部分检出到工作区，`--cone` 按目录、`--no-cone` 按 gitignore 风格模式。**易混点**：`--filter` 省的是**对象**，sparse-checkout 省的是**工作区文件**，两者常配一起用但解决的不是同一件事（第 10 章）。

**远端（remote）** — 就是一个**没有工作区的普通仓库**（对象库 + 引用）。**易混点**：所谓"远端"并不特殊，`git clone /path/to/repo` 与 `https://…` 在对象层面没有区别，只是传输方式不同（第 8 章）。

**refspec** — "源:目标"的引用映射语言，如 `+refs/heads/*:refs/remotes/origin/*`。**易混点**：开头的 `+` 表示**允许非快进更新**（fetch 时常见）；`:` 前留空表示**删除**（第 8 章）。

**`fetch` vs `pull`** — `fetch` 只更新 `refs/remotes/*` 与 `FETCH_HEAD`；`pull` = `fetch` + `merge`（或 `--rebase`）**并会改动你的本地分支与工作区**。**易混点**：`fetch` 永远安全，`pull` 不是（第 8 章）。

**want / have（协商协议）** — 客户端说"我要这个（want）""我已经有这些（have）"，服务端据此算出**最小 packfile**。**易混点**：这正是"传输量正比于新增对象、而非仓库总大小"的原因（实测每次只多 3 个对象）（第 8 章）。

**non-fast-forward** — 推送会丢掉远端已有的提交，Git 默认拒绝。**易混点**：拒绝不是报错，是保护——如果允许，已经躺在别人机器上的提交可能被无声丢掉（第 8 章）。

**`--force` vs `--force-with-lease`** — 前者无条件覆盖；后者"只有远端仍是我上次看到的样子才允许覆盖"。**易混点**：两者都不改变"改写历史会让别人分叉"这件事；`--force-with-lease` 保护的是**你的同事**（远端变了就报 `stale info`）（第 8 章实测）。

**`git ls-remote`** — 不克隆就问远端有哪些引用。**易混点**：附注标签会出现**两行**——`refs/tags/v2.0.1`（tag 对象）与 `refs/tags/v2.0.1^{}`（剥壳后的提交）（第 8 章）。

**promisor remote** — 部分克隆里"按需提供缺失对象"的那个远端。**易混点**：它由 `remote.<name>.promisor=true` 标记，不是你自己配的普通 remote 配置（第 10 章）。

## A.5　性能与底层

**delta 压缩** — packfile 里只存"与基准对象的差异"。**易混点**：它是"Git 存快照却不臃肿"的**唯一**原因；`--depth=1` 禁止深链，实测体积涨 **5.6×**（第 10 章）。

**`--depth` / `--window`（repack 参数）** — 控制 delta 链的最大深度与搜索窗口。**易混点**：`git clone --depth=1` 是**浅克隆**（另一件事），与 `git repack --depth` 同名但语义不同（第 10 章）。

**`git count-objects -v`** — 报告松散对象数（`count`）、打包对象数（`in-pack`）、pack 个数与体积。**易混点**：`count` 是**松散对象数**不是对象总数；总数要 `count + in-pack`（第 2、10 章）。

**`git verify-pack -v`** — 看某个 packfile 里每个对象的大小、delta 链长分布。**易混点**：它读的是 `.idx`，所以必须先有 pack（`gc`/`repack` 之后）才能用（第 2、10 章）。

**`git rev-list`** — 只做图遍历、不渲染输出的"底层 `log`"。**易混点**：`--count` 统计提交数、`--objects` 连对象一起列——后者是观察"可达集合大小"的最直接方式（第 10 章）。

**`GIT_TRACE_PERFORMANCE=1`** — 打印 Git 内部各相位耗时，最后一行是总计。**易混点**：`GIT_TRACE2_PERF=1` 更细（含是否读 commit-graph），但两者输出格式完全不同（第 10 章）。

**`GIT_TRACE_PACKET=1`** — 打印传输协议往返（能看到 `want`/`have`）。**易混点**：它输出到 stderr，且信息量巨大，一定要配 `grep`/`head`（第 8、10 章）。

**`git fast-import`** — 用流式指令批量建对象，可快速造几十万提交的测试仓库。**易混点**：它直接写对象库，不进索引与工作区，造完通常还要 `git reset --hard`（第 10 章）。

**plumbing（管道命令）** — 低层原语（`hash-object`/`mktree`/`commit-tree`/`update-ref`），给脚本用。**易混点**：与 porcelain（`add`/`commit`/`branch`）只是"面向谁"的区别，不是"能不能用"的区别（第 2 章）。

**`git mktree`** — 从 `模式 类型 哈希<TAB>名字` 的文本造一棵 tree。**易混点**：它只造 tree 对象，**不会**写工作区、也不动索引（第 2 章）。

**`git commit-tree`** — 用一棵 tree + 可选的 `-p` 父提交造一个 commit 对象。**易混点**：造出来的提交**不在 `git log` 里**——必须再 `git update-ref` 给个引用才会"可达"（第 2、3 章实测）。

**`git update-ref`** — 直接移动/创建引用，等价于"手工创建一个分支"。**易混点**：`git branch new` 与 `git update-ref refs/heads/new HEAD` 在结果上等价，后者不做任何校验（第 3 章）。

**`git symbolic-ref`** — 读/写符号引用（`HEAD`），`-q` 让 detached 时静默失败。**易混点**：它问的是"名字"，不是"值"——两者必须分开调用（第 3、12 章）。

**`git for-each-ref`** — 遍历所有引用并格式化输出（`%(refname)`、`%(objectname:short)`、`%(subject)`）。**易混点**：它比"读 `.git/refs/` 目录"可靠得多，因为引用可能在 `packed-refs` 里（第 3、11 章）。

**`git cat-file`** — 取对象的类型（`-t`）、大小（`-s`）或内容（`-p`）。**易混点**：`-p` 会按对象类型"漂亮打印"（tree 给列表、commit 给字段），而 `--batch-check` 给的是机器友好格式（第 2 章）。

**`git hash-object`** — 算（`-w` 时并写入）一个 blob 的哈希；`-t tree /dev/null` 可复现空树常量。**易混点**：哈希输入带 `类型 长度 NUL` 头，所以"文件内容一样但类型不同"哈希也不同（第 1、2 章）。

**`git diff-tree`** — 底层版的"某提交改了什么"，`-r` 递归、`--no-commit-id` 去掉首行。**易混点**：它默认不递归子目录，不加 `-r` 会只看到顶层条目（第 5 章）。

**`git diff-index` / `git diff-files`** — 分别是"HEAD↔索引"与"索引↔工作区"的底层写法。**易混点**：它们**不刷新 stat 缓存**，脚本里常用 `--quiet` 判断"有没有变"，而不是拿来给人看输出（第 4 章）。

**`git read-tree` / `git write-tree`** — 把 tree 读进索引 / 把索引写成 tree 对象。**易混点**：`write-tree` 是 `git commit` 内部第一步，它**不创建提交**（第 2、4 章）。

**`git update-index`** — 直接操作索引条目（`--add`/`--cacheinfo`/`--refresh`/`--assume-unchanged`）。**易混点**：`--cacheinfo` 的写法是 `模式,哈希,路径` 三个逗号分隔字段，很容易写错顺序（第 4 章）。

**`git pack-objects` / `git index-pack`** — 生成 packfile / 校验并索引一个 packfile。**易混点**：它们是服务端 `fetch` 服务的核心，日常几乎不用直接调（第 8、10 章）。

**`git multi-pack-index write`** — 为多个 packfile 建一层合并索引。**易混点**：它不减少 pack 个数，只是让对象查找不必逐个读 `.idx`（第 10 章）。

**`git maintenance run`** — 按任务粒度跑后台维护（`--task=commit-graph` 等）。**易混点**：它是 `gc` 的现代化替代，可以做增量任务而不是"全量重打"（第 10 章）。

**只读命令（read-only commands）** — `diff`/`log`/`ls-files`/`rev-parse`/`symbolic-ref` 这类不改动仓库状态的命令。**易混点**："只读"是指**不改对象库与引用**，不是"不写任何文件"——它们仍可能刷新 stat 缓存，所以还要配 `GIT_OPTIONAL_LOCKS=0`（第 9、12 章）。

## A.6　工具与工程

**hook（钩子）** — Git 在特定时机调用的**可执行文件**，默认在 `.git/hooks/`。**易混点**：启用方式是"去掉 `.sample` + 加执行权限"，而且**钩子不进版本库**，克隆不会带走（第 11 章）。

**客户端钩子（client-side hooks）** — `pre-commit`、`commit-msg`、`pre-push`、`pre-rebase`，在你自己执行命令时跑。**易混点**：它们**可被 `--no-verify` 绕过**，所以只能当"便利"，不能当规范（第 11 章）。

**服务端钩子（server-side hooks）** — `pre-receive`、`update`、`post-receive`，在收到推送时跑。**易混点**：客户端**无法绕过**——实测 `git push --no-verify` 依然得到 `! [remote rejected] (pre-receive hook declined)`（第 11 章）。

**`--no-verify`** — 跳过客户端钩子。**易混点**：它对服务端钩子**完全无效**，这是"团队规范必须放到服务端或 CI"的直接理由（第 11 章）。

**`core.hooksPath`** — 把钩子目录指到仓库内的 `.githooks/`，让团队能共享脚本。**易混点**：它仍然要**每个成员各自设置一次**，不是克隆就自动生效（第 11 章）。

**签名（GPG / SSH signing）** — 给提交或 tag 附加密码学签名。**易混点**：SSH 签名（`gpg.format=ssh`）**不需要 gpg**，复用你已有的 SSH key；验证还需要一份 `gpg.ssh.allowedSignersFile`（第 11 章）。

**`git verify-commit` / `git verify-tag`** — 验证签名，输出 `Good "git" signature for …`。**易混点**：未签名的提交会让 `verify-commit` 以**非零退出码**结束——脚本里别把它当"验证失败"之外的普通错误（第 11 章、附录 B 实测）。

**发布闸门（gate job）** — 发布流水线里"构建之前必须先过"的那一段（vet / gofmt / test -race / node --test）。**易混点**：它的价值来自**一次真实事故**——v1.8.0 "打 tag 直接发布"漏出三个线上问题，v1.8.2 才补上闸门（第 11 章）。

**冒烟测试（smoke test）** — 发布后按"用户实际会走的那条路"验证（装包 → 跑命令 → 看输出）。**易混点**：两段式冒烟是刻意的——先做不依赖 registry 传播的确定性检查，再做传播后的验证（第 11 章）。

**`git bugreport`** — 生成一份包含版本、配置与系统信息的缺陷报告模板。**易混点**：默认文件名是 `git-bugreport-<时间戳>.txt`；**同一分钟内重复执行会因文件已存在而失败**（`fatal: unable to create …: File exists`，退出码 **128**）。要规避撞名得用 `-s <后缀>`（如 `-s a` → `git-bugreport-a.txt`）；**`-o <目录>` 只改位置、不改名**，规避不了（附录 B、D.3 实测）。

**`git diagnose`** — 收集诊断包（`--mode=all` 最全），输出到一个 zip。**易混点**：它比 `bugreport` 重得多，且产物含仓库结构信息，公开前先看一眼内容（附录 B 实测）。

**`GIT_TERMINAL_PROMPT=0`** — 禁止 git 弹出凭据提示，宁可失败也不挂起。**易混点**：在 CI/agent/cron 里这不是优化而是必需——一个"等密码"的 git 进程会让整条流水线挂到超时（第 8、12 章）。

**`GIT_PAGER=cat` / `--no-pager`** — 禁止分页器。**易混点**：在管道/非 TTY 环境里，分页器会让进程**挂住**；两者通常一起用（第 8、12 章）。

**`GIT_OPTIONAL_LOCKS=0`** — 让只读操作不去抢 `.git/index.lock`。**易混点**：它只是让"选择性加锁"的那些操作放弃加锁，从而避免与用户并发操作互相干扰；需要写锁的命令不受它影响（第 12 章）。

**`-z`（NUL 分隔输出）** — 让 `--name-status`、`ls-files` 等以 NUL 分隔。**易混点**：路径里可以出现空格、制表符、换行、引号，**NUL 是唯一不可能出现的字节**，所以"按行 + 按空白切分"的解析必然在某些仓库上崩掉（第 12 章）。

**0x1F 分隔符（Unit Separator）** — 自定义 `--format` 字段时用的控制字符分隔符。**易混点**：作者名与提交信息里**什么都可能出现**（含 `|`、逗号、换行），只有控制字符安全——原则是"永远不要用可能出现在数据里的分隔符"（第 12 章）。

**`shortSHA`（短哈希）** — 取哈希前 7 位用于展示。**易混点**：超大仓库里硬截 7 位理论上有歧义风险，Git 自己会自动加长到无歧义；展示可以偷懒，当**唯一标识**去查询就不行（第 3 章）。

**diff 口径（diff semantics）** — "这次改动到底是相对谁算的"这个约定。**易混点**：合并提交取第一父 = GitHub 的 PR diff = "这次合并给主线带来了什么"；口径必须写进产物，否则用户不知道你在说什么（第 5、12 章）。

**hardening（加固）** — 让工具在任意用户环境里都不会挂掉、不会被改写的那些固定参数与环境变量。**易混点**：它们的共同点是"**不去猜用户配置，而是把协议固定下来**"——用户的配置是环境的一部分，不是你的接口（第 12 章）。
